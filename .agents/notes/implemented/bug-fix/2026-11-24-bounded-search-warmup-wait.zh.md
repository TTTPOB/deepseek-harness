# Agent Note: 搜索预热的有限等待

Status: implemented

[English](2026-11-24-bounded-search-warmup-wait.md) | 中文

## 问题

SQLite 提供方在后台 worker 中预热索引。在预热完成前，跨会话搜索会立即返回 `SESSION_QUERY_INDEX_WARMING`。对一个安装环境 14 天记录的审计发现，3 个会话里共有 14 次这样的失败；其中一次，7 个不同查询几乎同时被拒。这个错误可以重试，但模型会把它当成搜索失败；有意不重试提供方请求的会话工具也会把它直接交给模型。

## 决策

`searchSessions` 最多等待 [`warmupWaitMs`](../../../../packages/session-query/session-query-sqlite/README.zh.md) 毫秒，等的是已在进行的预热；默认 3000，设为 `0` 时立即返回。等待只观察服务自己持有的那次预热，不会另起扫描。预热在等待期内完成，搜索照常进行；预热失败，搜索报告该失败；等待超时，搜索以 `SESSION_QUERY_INDEX_WARMING` 失败。取消请求只结束该请求自己的等待。使用 `openAt: first-search` 时，首次搜索先启动预热，再按同样方式等待。`searchEvents` 不变：文档键就绪后，它只刷新目标会话，不等待全部历史。该配置接受 0 到 2,147,483,647 的整数，上限是 `setTimeout` 能接受的最长延迟。

## 考虑过的替代方案

**一直等到预热完成。** 上游 DeepSeek Harness 在首次搜索返回前打开并核对整个索引。在 1,000 个会话的语料上，首次搜索约需 144 秒（[语料性能基线](../testing/2026-09-28-session-corpus-performance.zh.md)），远超实验性搜索工具 30 秒的默认超时。

**由每个消费方重试。** 每个消费方都要有自己的重试循环和预算，禁止重试提供方请求的会话工具得放弃这条规则，而模型重试时不会退避。

**较长的默认等待。** 接近工具超时的等待会让 PTC 程序和并行调用都卡在一次缓慢的预热上。3 秒的默认值只是为增加的延迟设上限，不是根据实测预热时长得出的；预热时长取决于语料规模。

## 后果

预热期间，跨会话搜索最多多花 `warmupWaitMs` 才成功或失败。在预热即将完成时到达的搜索会成功，而不是失败。预热时间较长时，等待结束后仍返回 `SESSION_QUERY_INDEX_WARMING`。希望立即得到结果的部署可将 `warmupWaitMs` 设为 `0`。
