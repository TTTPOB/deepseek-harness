# Agent Note: 会话搜索的查询语法与排序

Status: implemented

[English](2026-11-28-session-search-query-syntax.md) | 中文

## 问题

原来的全文查询要求整句短语相邻，加入第二个词往往就找不到原有的有用结果。日常使用中积累的数据显示，`academic-source CLI` 等 6 次多词查询全空，换成 `academic` 即命中。`molbench AND timeout` 中的 `AND` 被当作字面词，连续 5 次搜索无结果。一个安装环境的 296 次成功搜索中，85 次没有命中。

## 决策

[SQLite 提供方](../../../../packages/session-query/session-query-sqlite/README.zh.md#search-behavior)自行解析查询并生成短语加引号的 FTS5 表达式。空格和大写 `AND` 要求各项都出现在同一个事件中；大写 `OR` 优先级更高。双引号要求词元连续；括号分组；紧贴在项前的 `-` 排除该项；裸词末尾 `*` 匹配前缀。其余标点是字面查询数据，正文和查询项都由 `unicode61` 分词。不含词元的项会被忽略。

引号或括号不配对、空括号组、括号嵌套超过 16 层、`OR` 缺操作数、AND 组或 OR 分支缺少正向项都视为无效。整个查询只有排除项时返回 `SESSION_QUERY_EXCLUSION_ONLY`，Web 会话列表会把整段文本作为一个字面短语重搜。没有可搜索词元时返回 `SESSION_QUERY_INVALID_QUERY`。

`searchEvents` 返回全库或指定一组会话中的单条事件命中。每条命中带会话头信息；给出确切 ID 时，可按[有限预热等待决策](../bug-fix/2026-11-24-bounded-search-warmup-wait.zh.md)刷新指定会话，而无需等全库预热结束。

### 排序

单短语查询保持原来的排序。复合查询使用完整表达式和元数据过滤器选出各索引的候选文档。每个正向短语在每个来源用一个打分 `MATCH` 游标遍历倒排记录；`CROSS JOIN` 先按 rowid 确认该文档在候选集合里，再调用 `bm25`。每个短语以同一套历史 IDF 和文档平均长度对两部分打分；实时原生分数用于反推重算所需的整数词频。反推历史 IDF 的舍入误差可能使不同来源中正文相同的文档产生 1e-12 量级的分差，因而它们的先后不一定按事件时间排列。不同的正向短语得分相加；OR 中没有出现的短语和被排除的项贡献为零。高亮使用完整表达式。

## 考虑过的替代方案

**直接合并两部分的原生分数。** 两份索引的 IDF 和平均长度不同。同样的文档仅因一份来自运行中会话就可能得分不同，合并排序会有偏差。

**逐个候选行发起 FTS MATCH。** `rowid = ?` 约束无法消除重新打开常见短语的代价。重复打分的开销接近二次增长；每个短语走一次游标，再按 rowid 查候选集合，能保留相同分数。

**空格表示 OR。** 加入用于缩小范围的词时，只含一个常见词的事件也会返回，使模型看到的有界结果更杂。

## 后果

用户可以不猜词序就放宽或缩小搜索范围。AND 始终要求词项出现在单条事件中，不会合并同一会话的多条事件。[跨来源排序测试](../../../../packages/session-query/session-query-sqlite/tests/store-ranking.spec.ts)验证不同索引统计下的相同正文得分完全相等，并用另一用例限制舍入误差。
